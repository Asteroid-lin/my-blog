# OMS 设计思考

> 本页记录分析 OMS 时的判断方法和待验证的设计取舍，不把通用方案当作当前项目已实现的架构。

## 先划清业务边界

面对一条订单链路，先问“谁拥有这条事实”。[订单中心](./order-center.md)保存客户买了什么与交易状态；[库存中心](./inventory-center.md)管理可承诺数量和占用；[履约中心](./fulfillment.md)决定由谁、从哪里、以什么方式发；WMS 执行仓内作业；财务系统确认账务和资金结果。一个状态可以被多个系统读取，但需要明确哪个系统有权产生和修正它。

## 从场景推导约束

每项设计先覆盖正常、失败和逆向场景。例如“下单后寻仓发货”至少追问：最后一件货被并发订单争用怎么办？库存锁定成功但 WMS 下发超时怎么办？WMS 已出库而客户取消怎么办？部分发货、拒收、退货会改变哪些数量和状态？这些问题决定单据关系、幂等键、回传事件和补偿规则。

## 决策记录模板

| 项目 | 应记录的内容 |
| --- | --- |
| 背景 | 业务模式、当前问题、涉及系统与已知事实 |
| 约束 | 时效、并发、财务口径、外部系统能力及不可改变的契约 |
| 候选方案 | 至少列出可执行的处理路径及对状态、库存的影响 |
| 取舍 | 选择原因、放弃原因、风险和异常回退方法 |
| 验证 | 用哪些订单、接口日志、数据表、回调或对账结果证实 |

例如库存锁定时点：可以在订单放行时锁，也可以在寻仓确定仓后锁。选择取决于库存粒度、寻仓耗时、锁定过期策略和失败后的释放能力。不能只写“下单即锁库存”，还要说明哪个订单行、哪个仓、锁多久，以及取消和部分出库如何结清。

## 图与证据的层次

- **业务全链路图**说明渠道到订单、库存、履约、WMS、物流、售后和财务如何交接，重点是业务动作与异常分支。
- **模块业务逻辑图**说明一个模块的输入、校验、分支、回传和失败恢复，例如寻仓与库存分配。
- **技术架构图**才标出服务、接口、消息、数据库和部署组件。

先由业务资料确认动作和责任方，再用代码、接口及日志验证技术实现。图上未核实的规则应标为示意或待确认，不应从某个类名推断完整生产流程。
