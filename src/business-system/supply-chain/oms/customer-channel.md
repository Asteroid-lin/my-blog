# 客户与渠道

> 本页整理项目现有“多渠道订单、经销商、直营、采销和一件代发”的业务范围。主体归属、信用与结算规则仍需业务和财务确认。

## 业务目的与参与角色

客户与渠道资料用于识别订单从哪里来、卖给谁、由谁发货以及与谁结算。渠道/店铺运营方维护售卖入口，客户管理方维护交易主体，OMS 将渠道订单转成统一订单，履约与财务分别使用其发货和结算维度。

## 不同主体的职责

| 对象 | 主要作用 | 容易混淆的点 |
| --- | --- | --- |
| 渠道 | 标识淘宝、京东、抖音、直营等订单来源 | 渠道不是客户，也不一定是结算主体 |
| 店铺/渠道账号 | 定位渠道内的订单和商品映射范围 | 同一渠道可有多个店铺，外部订单号需结合来源识别 |
| 下单人与收货人 | 表达购买及配送信息 | 可能与交易客户、开票主体不同；地址和联系方式属于订单数据 |
| 交易客户 | 标识经销商、企业客户等购买主体 | 决定业务模式，不能直接等同于收货人 |
| 结算客户 | 对账、应收和开票面向的主体 | 可能与交易客户不同，需财务规则确认 |
| 供应商/代发方 | 在指定模式下承担供货或直发 | 不是购买客户，应单独维护履约关系 |

客户与渠道主数据宜保留稳定的主体身份、编码和关系；收货地址、联系人、成交价格、信用余额等随订单或财务业务变化的数据，应按对应业务记录和权限管理。

## 接单识别流程

```text
渠道 + 店铺 + 外部订单号
  → 找到内部渠道/店铺关系与订单来源
  → 识别交易客户、业务模式和销售组织
  → 映射渠道商品并生成统一订单
  → 按业务模式选择审核、库存、履约和结算规则
```

外部订单号应与来源渠道、店铺一起使用，防止不同渠道出现相同编号。经销、采销、直营零售和一件代发识别出来之后，分别进入[业务模式](./business-mode.md)中的放行、库存和结算规则，不能共用一套。客户或渠道映射缺失时，订单应进入待处理状态并留下原始来源信息，便于补齐资料后重试。

## 与履约和结算的关系

- **履约**读取业务模式、收货地区、可用履约节点及供应商直发关系；最终寻仓和拆单由[履约中心](./fulfillment.md)负责。
- **财务**根据交易主体、结算主体、销售组织及合同/账期等规则处理应收、对账和开票；详见[财务与结算](./finance-settlement.md)。
- **历史订单**保留交易主体、渠道/店铺及必要名称快照；主体改名或关系调整不能改变已发生交易的归属。

## 资料控制与待确认问题

渠道、店铺、客户和供应商编码应能追溯来源系统，映射关系需要状态和生效时间。停用店铺或客户前，应核查未完成订单与售后单。涉及个人收货信息时，只让必要流程读取，并避免把完整联系方式写入主数据同步日志。

- 一个店铺是否固定对应一个销售组织？同一客户能否跨渠道、跨组织交易？
- 经销、采销、直营和一件代发分别如何识别？交易、开票、结算及发货主体如何组合？
- 信用额度、账期和价格体系由哪个系统决定？OMS 在哪个节点校验？
- 客户合并、店铺迁移、供应商停用后，历史订单和在途履约如何保持可追溯？
