# OMS 学习与输出路线

沿业务地图、典型单据、开发设计和验收证据逐步推进。每一阶段都记录已核实规则与未确认事项，再决定下一阶段的实现范围。

## 第一阶段：建立业务地图

从[OMS 总览](./README.md)开始，沿阅读表把链路走完：主数据、[业务模式](./business-mode.md)、审单、支付、寻仓锁定、包裹回传、售后和财务。用[单据、状态与库存流水](./domain-model.md)统一对象和状态。输出一张业务全链路图和一份术语表，注明实际业务模式与仍待核实的分支。

## 第二阶段：走通核心场景

先按[业务覆盖与缺口清单](./business-coverage.md)圈出实际启用的模式。组合赠品、预售、调拨、经销、直发、自提、换货补发和批次追溯至少各保留一个适用示例；未启用的业务记录入口限制，避免读过专题就当作系统支持。

各选一笔正常发货、审单挂起、支付超时、缺货、部分发货、改地址、拦截、退货/退款、报修订单，按时间列出输入、状态、数量、金额、外部单号和责任系统。重点核对订单行、库存占用、履约任务和包裹，而不是只记住一个主订单状态。报修要另外看保修期、维修方式和配件，不要把它当成退货。

## 第三阶段：连接代码与数据

把业务动作映射到入口接口、应用服务、持久化记录、消息或回调和对账任务。针对每个动作核实：谁发起、谁是权威来源、唯一业务键是什么、重复请求怎么处理、失败后如何恢复。输出“业务动作 → 接口/消息 → 代码 → 数据表/日志”的索引，并标注验证环境和证据。

## 第四阶段：形成可复用说明

按[OMS 设计思考](./design-thinking.md)记录有争议的取舍，补充模块业务逻辑图与异常分支。经业务、仓储和财务相关人员核对后，将各页“待确认问题”改成有来源的规则；仍无证据的内容继续标为示意。

## 固定记录模板

每个主题按“**业务目的、参与角色、业务流程、核心数据、系统实现、异常与补偿、待确认问题**”记录。业务结论附来源文档或真实单据，技术结论附代码位置、接口契约或运行日志；静态代码存在不等于生产功能已经启用。

## 从学习材料进入系统建设

学习阶段产出的业务地图和问题清单，进入[建设范围与实施路线](./construction-plan.md)后要转成可交付任务：

| 学习输出 | 开发输出 | 检查入口 |
| --- | --- | --- |
| 全链路和典型订单 | 输入、状态、数量及异常的场景记录 | [业务场景与单据推演](./business-scenarios.md) |
| 模块职责和权威来源 | 模块接口、事务边界、调用链 | [模块架构与事务边界](./technical-architecture.md) |
| 单据、状态和数量关系 | 表关系、唯一键、余额与流水约束 | [数据模型与约束](./data-design.md) |
| 外部单号与交互流程 | 命令、事件、错误及幂等约定 | [接口与事件契约](./api-contracts.md) |
| 异常和补偿清单 | 任务、查询、回放、对账及受控修复 | [一致性与恢复设计](./consistency-recovery.md) |
| 操作角色和业务时限 | 页面权限、审计、指标与责任人 | [运营工作台与权限](./operations.md) |
| 业务规则与运行证据 | 可重复场景、故障注入及准入结果 | [测试与上线验收](./acceptance.md) |

后续在 [Mini OMS](../../../projects/mini-oms/README.md) 记录实际代码仓库、完成阶段、联调证据和未完成项。文档设计完成不等于后端实现完成。
