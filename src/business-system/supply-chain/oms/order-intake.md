# 渠道接单、补单与订单变更

> 本页补充渠道订单如何持续、完整地进入 OMS。渠道协议未确定，下面按“推送为主、补拉核对、人工导入可审计”的设计基线展开。

## 业务目的与参与角色

渠道提供交易和变更事实，运营处理映射与导入错误，OMS 将来源订单转为统一单据。需要保证的不只是“不重复建单”，还包括“不漏单、不把旧版本盖成新状态、不在渠道已取消后继续发货”。

## 三种入口共用一条业务链

| 入口 | 适用情况 | 必须保留的来源信息 |
| --- | --- | --- |
| 渠道推送 | 下单、支付、取消和售后事件 | 店铺、事件号、外部订单号、版本、接收时间 |
| 定时补拉 | 推送丢失、系统停机、差异核查 | 拉取区间、分页游标、水位、原始响应摘要 |
| 人工导入 | 线下订单、首次迁移、异常补单 | 导入批次、行号、业务单号、上传人与审核人 |

```text
认证来源 → 原始数据落库 → 来源订单去重与版本核对
  → 商品/主体映射 → 数量、金额及渠道能力校验
  → 建单或登记变更命令 → 审单与放行
  → 返回接单结果，待处理项进入工作台
```

人工导入也必须有稳定业务单号；不能以 Excel 行号充当订单唯一键。相同文件换个名字或同一行移动位置，仍应识别为相同业务。导入先预检，分别列出可接收、已存在、冲突和缺资料行，再保存逐行结果。

## 补拉如何避免漏单

使用渠道提供的更新时间范围或增量游标，记录固定本批截止水位。完整接收并持久化所有分页后才推进批次水位，失败则从保存的检查点继续。时间窗口适当重叠并用来源键去重，处理迟到和边界相等的记录。

若只提供 offset 分页且拉取期间数据会变化，应使用固定查询窗口、稳定排序和重复扫描对账；不能在会变化的结果集上翻完页就认定没有遗漏。库存/支付等独立事件也要有自己的补拉进度，不共用一个订单水位。

## 新建、修改、取消要分开

| 来源变化 | OMS 的处理 | 禁止的捷径 |
| --- | --- | --- |
| 相同订单、相同版本与内容 | 返回已接收结果 | 再建一张单 |
| 相同版本、不同关键内容 | 记录冲突，查来源并挂起 | 静默覆盖金额、SKU 或地址 |
| 新版本修改地址或数量 | 保存变更单与修订，按执行阶段处理 | 绕过拦截直接修改已下发任务 |
| 旧版本迟到 | 留存记录，不回退已确认事实 | 根据接收时间认定它最新 |
| 渠道取消与出库交错 | 按未发量和对端最终裁决处理 | 把渠道“已取消”直接覆盖 WMS 出库事实 |

来源不提供版本时，可比较规范化快照并查询渠道当前详情；顺序仍不明时挂起冲突。接单 API 的幂等冲突不等于允许忽略合法改单：改单必须建立独立命令，见[改单与拦截](./order-change.md)。

## 支付先到、取消先到和店铺停用

支付先到时保存待关联记录；订单到达后校验商户、外部单号、币种和金额再关联。取消先到时保存来源取消标记，后续补到订单不得自动放行；查明最终交易结果后决定关闭与退款。

店铺停用区分“停止新接单”和“已有业务继续收尾”。在途出库、退款、售后及对账仍需接收；凭证失效时停止自动处理并通知负责人，修复后从原水位补拉。不能删掉店铺映射导致历史单据失联。

## 核心数据与开发落点

在[一期模型](./data-design.md)之外补来源订单记录、导入批次与行结果、同步检查点、来源变更单。原始记录可以尚未映射成 OMS 订单，状态包括待映射、待关联、冲突、已转换和拒绝。保存来源外部行号，不用 SKU 合并不同价格或不同售后来源的行。

渠道能力表至少记录：是否支持部分发货、改单、取消查询、增量拉取、事件版本及补运单。履约策略读取能力表；渠道不支持的操作不能在内部成功后才发现回传不了。

## 验收与待确认

- 推送与补拉同时带来同一单，只建一次；拉取中断重启后补齐全部分页。
- 取消先到、支付先到都能正确关联，不出现误发货或重复收款记录。
- 修复导入错误行后重试，成功行不重复建单，原始内容及修复理由可追溯。
- 待确认：各渠道唯一键、版本含义、补拉时间精度、历史可查范围，以及停止合作后的未结业务处理人。
