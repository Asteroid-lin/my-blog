# 接口与事件契约

> 以下为未来 OMS 内部统一契约的草案。地址、字段、状态码需要在后端创建时固化为 OpenAPI；外部渠道与 WMS 的真实协议通过适配器转换，不能直接拿本文调用生产系统。

## 先统一三个标识

| 标识 | 用途 | 生命周期 |
| --- | --- | --- |
| `requestId` | 一次业务命令的去重，例如下发、取消、退款 | 同一命令重试不变；改变仓或数量应建新命令 |
| `eventId` | 一条来源事件的去重，例如出库通知 | 来源重发必须不变；按来源系统区分作用域 |
| `traceId` | 串联某次调用日志 | 每次重试可以不同，不能用作业务幂等键 |

命令幂等范围为“可信来源/经营主体 + 动作 + requestId”。服务器保存规范化业务载荷摘要：同键同内容返回原结果，同键不同内容返回冲突；不能把第二份不同数量的请求当成成功重试。金额、币种、仓库、行数量都纳入摘要，traceId 等传输字段不纳入。

## 一期接口清单

| 方法与草案路径 | 输入重点 | 返回含义 |
| --- | --- | --- |
| `POST /api/oms/v1/orders` | 来源店铺、外部订单与行号、快照、金额、requestId | 本地接单结果，可能待映射或待审 |
| `GET /api/oms/v1/orders/{orderNo}` | 有权限访问的订单号 | 头行、分配、包裹、取消及售后摘要 |
| `POST /api/oms/v1/orders/{orderNo}/audit-decisions` | 通过/挂起、原因、expectedVersion | 审单结果，不代表已占库存 |
| `POST /api/oms/v1/orders/{orderNo}/allocations` | requestId、expectedVersion、分配策略 | 分配明细及下发命令号 |
| `POST /api/oms/v1/orders/{orderNo}/cancellations` | requestId、逐行申请数量、原因 | 取消申请号，部分行可能等待拦截 |
| `POST /api/oms/v1/aftersales` | 原行/包裹明细、类型、数量、原因 | 售后申请号，不表示退款已完成 |
| `GET /api/oms/v1/commands/{requestId}` | 命令号及所属动作/来源 | 待执行、处理中、未知、成功或失败 |
| `POST /integration/v1/payment-events` | 支付方流水、金额、币种、外部订单号 | 已持久化接收的事件号 |
| `POST /integration/v1/shipment-events` | 任务、包裹、出库明细号及本次数量 | 已持久化接收的事件号 |
| `POST /integration/v1/cancellation-events` | 拦截请求、最终结果、逐行确认数量 | 已接收；订单取消另按业务规则处理 |
| `POST /integration/v1/return-receipt-events` | 售后行、收货明细号、良品/残次数量 | 已接收；库存变化需等待业务处理 |
| `POST /integration/v1/refund-events` | 退款请求号、原支付、最终结果 | 已接收；资金状态按结果幂等推进 |

命令查询必须限定来源、动作和权限范围，不能仅凭可猜测的 requestId 跨主体查数据。接入方身份决定可操作店铺、货主和仓库，不接受请求体任意指定后就信任。

## 取消请求示例

```json
{
  "requestId": "cancel-O1001-001",
  "expectedVersion": 7,
  "reason": "客户取消未发商品",
  "lines": [
    { "orderLineId": "L2", "quantity": 1 }
  ]
}
```

```json
{
  "code": "ACCEPTED",
  "data": {
    "cancellationNo": "C1001",
    "status": "WAITING_INTERCEPT",
    "lines": [
      { "orderLineId": "L2", "requestedQty": 1, "confirmedQty": 0 }
    ]
  },
  "traceId": "trace-example-001"
}
```

这里可返回 HTTP 202，表示申请已持久化，仍需等待 WMS。客服页面应展示“拦截中”，不能立即显示“已取消、已退款”。成功结果应有逐行已取消、拒绝和未知数量。

## 出库事件示例

```json
{
  "schemaVersion": 1,
  "eventId": "wms-event-10001",
  "source": "WMS-DEMO",
  "eventType": "SHIPMENT_CONFIRMED",
  "occurredAt": "2026-10-04T10:30:00+08:00",
  "requestId": "dispatch-F1-001",
  "taskNo": "F1",
  "packageNo": "P1",
  "shipmentNo": "WS1001",
  "lines": [
    {
      "shipmentLineNo": "1",
      "allocationId": "ALLOC-L1-W1",
      "skuCode": "SKU-A",
      "quantity": 2
    }
  ]
}
```

本契约的 quantity 是**本次出库增量**，不是任务累计已发量。去重同时覆盖 eventId 和“来源 + shipmentNo + shipmentLineNo”；同一出库明细换 eventId 重发也不能二次扣减。同一明细内容冲突必须隔离为异常。

如果外部只提供累计数量，适配器必须按任务行持有来源版本，在锁内计算新累计减旧累计；旧版本拒绝覆盖。没有稳定明细号或版本时，不能简单用事件时间猜测，需与对端补契约或转查询核对。

## 顺序与错误如何表达

| 情况 | 草案响应或业务结果 | 调用方动作 |
| --- | --- | --- |
| 同键同内容重复 | 返回原命令或事件结果 | 不建新单 |
| 请求结构或数量非法 | `400 INVALID_ARGUMENT` | 修正输入 |
| 无身份或无权限 | `401` / `403` | 修复身份和权限 |
| 同键不同内容、版本过期 | `409 IDEMPOTENCY_CONFLICT / VERSION_CONFLICT` | 读取现状，人工或业务决定新命令 |
| 当前状态不允许动作 | `409 STATE_CONFLICT` | 刷新状态并按允许流程处理 |
| 接收成功待执行 | `202 ACCEPTED` | 查命令结果或等后续通知 |
| 限流或临时不可用 | `429` / `503` | 按退避策略重试同一命令 |
| 客户端超时 | 本地记 `UNKNOWN`，不是业务失败 | 按原 requestId 查询，不另起命令 |

错误码在真实适配器中需做映射；例如对端要求 200 加业务码时按其协议回复。数据库不可用、事件未落库时不能返回已接收。HTTP 成功、对端受理、业务执行成功是三个阶段，应分别记录。

## 扩展业务的契约检查点

| 业务交互 | 需要补充的稳定业务标识 | 需要明确的结果语义 |
| --- | --- | --- |
| 渠道增量补拉/改单 | 店铺、来源订单版本、游标/水位、变更号 | 新建、修订、取消及待关联分别返回 |
| 采购/调拨协同 | 供应批次、需求、出入库明细号 | 确认量、发出量、实收良品/残次量及差异 |
| 供应商或门店受理 | 原下发请求、节点裁决明细及版本 | 已接受、最终拒绝、未知和部分受理区分 |
| 自提核销 | 门店、自提任务、核销流水、实际提货行 | 授权身份和已提量，不能映射为虚构运单 |
| 信用授权/转换 | 合同、授权号、发货或取消来源明细 | 额度确认、冻结、转换、释放及未知结果 |
| 售后新发 | 售后批准行、独立新发需求、原包裹 | 区分销售初次交付与换货/补发交付 |
| 批次/SN 回传 | 库存维度、出入库明细、序列号作用域 | 质量、实物身份、数量和来源水位 |
| 账单/开票 | 账单版本与明细、开票申请、外部票据引用 | 已接收、已处理、最终成功及调整分别确认 |

这些是启用专题前需要补充的契约，不属于上面一期接口已经实现的功能。具体对象关系见[数据模型扩展](./data-design.md)，每个对端先收集真实请求、响应、重复与超时样例，再冻结接口。

## 契约演进与验证

时间携带时区，接收时间另由 OMS 记录；金额使用币种和最小单位，数量指明单位。签名或认证在适配器内按真实协议实现，凭据从部署配置读取，不进入日志与报文展示。

兼容新增可选字段也要明确缺省行为；改变数量含义、状态语义或必填字段要升级契约并保留过渡策略。用固定样例验证正常、重复、冲突、乱序、未知结果、签名失败和部分成功；完整用例见[测试与上线验收](./acceptance.md)。
