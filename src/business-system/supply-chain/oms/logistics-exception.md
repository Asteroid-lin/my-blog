# 物流异常、拒收与赔付协同

> 运单轨迹描述运输进度，客户处理与承运商理赔是关联但独立的业务。OMS 保存事实、诉求与处置，不把“查不到轨迹”自动当成丢件。

## 异常从哪里发现

| 异常 | 核查证据 | 建议下一动作 |
| --- | --- | --- |
| 有运单但未出库 | WMS 执行进度、面单申请结果 | 找仓库处理，不能标已发货 |
| 已出库长期未揽收 | 仓库交接记录、承运商扫描 | 查询交接，区分回调迟到与实际未交接 |
| 在途停滞或超承诺 | 轨迹、运输服务及异常地区 | 承运商查询、客户沟通、更新预计 |
| 地址异常/派送失败 | 地址快照、承运商错误原因 | 核实后申请改派或退回，保留申请结果 |
| 拒收/退回中 | 退回运单、实际目的仓 | 建逆向通知，等收货质检 |
| 丢失/破损 | 客户证据、交接和承运商调查 | 建异常案件，审批退款或补发及索赔 |
| 签收争议 | 签收凭据、代收人/地点、客户反馈 | 调查争议，不以一个签收状态驳回所有诉求 |

超时阈值来自配送服务和承诺，按揽收、在途、派送阶段分别配置。短信或站内信投递成功只表示通知送达记录，不代表客户认可处置。

## 异常处理闭环

```text
监控或客户反馈 → 关联包裹、运单、订单行和数量
  → 收集仓库/物流证据 → 明确责任人与处理期限
  → 查询、改派、退回、退款或补发审批
  → 执行客户处置 + 独立跟踪承运商索赔
  → 核对物流、实物及资金结果 → 复核关闭
```

同一包裹可以包含多个订单行，甚至来自多个订单。异常按受影响包裹明细记录，不能整包丢了就把所有相关订单的其他已签收包裹一起退掉。

## 拒收并不立即回补库存

客户拒收后，保存退回指令、逆向运单和收货目的地。正向包裹保持原已出库事实，逆向收货按新收货明细幂等处理；只有质检为可售的数量才增加良品库存。

退款可在业务批准的节点发起，但退款成功不增加库存。若先退款后收货，案件仍需追踪退回；承运商确认丢失时也不能虚构一笔退货入库来结案。

## 丢损、补发和赔付分开记

建议以异常案件连接三条进度：客户是否已退款/补发、货物是否找到/退回/报损、承运商索赔是否受理/认可/回款。客户诉求可以先获批准，但承运商未认可的索赔金额不能当作已回款。

例：包裹 A 1 件丢失，经审批免费补发 1 件。原包裹仍为已出库并处于丢失异常，新包裹属于[售后发货需求](./exchange-reship.md)，不会把原订单购买数量变成 2。之后原包裹找到并被客户签收，重新开启该案件处理重复交付，不再自动补发或退款一次。

赔付金额、运费承担、客户补偿及供应商扣款分别保留批准依据与外部结果，由财务核对，不能互相抵消后只存一个净额。

## 改派、换运单与历史轨迹

改派请求不是直接改订单地址：保存新的运输指令和承运商结果，原下单地址与原出库快照保持可追溯。无法更改时按客户同意的退回或其他方式处理。

换运单保留旧新运单的有效期和关系。旧号作废需要执行方确认，已有有效运输任务时禁止仅因申请超时又开第二张单。退回运单与正向运单分开，不以新号覆盖旧号导致丢失轨迹。

## 数据、验收与待确认

增加物流异常案件、影响明细、证据引用、处置决定、运输变更请求和索赔跟踪；敏感签收凭据采用受控访问。客户、仓库、承运商与财务责任和处理时限独立记录。

验收覆盖：未揽收补拉后恢复、重复轨迹不重复开案件、拒收未入库不增可售、一包部分破损只处理对应量、补发后原包找回可追踪、索赔回款不重复入业务汇总。

待确认：揽收时限、丢失裁决方、签收争议处理人、承运商查询/改派能力、退回收货仓及哪些客户处置需要审批。
