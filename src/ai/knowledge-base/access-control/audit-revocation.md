# 访问审计与权限变更

审计记录谁在何时对什么资源做了什么、结果如何；权限变更则保证新的访问规则能落实到查询、任务、缓存和历史记录。所属场景：[多租户与权限隔离](./README.md)。

## 业务目标与责任

租户管理员负责成员与角色，知识库管理员负责资源授权，审计人员按职责查看记录，运维负责权限同步与异常恢复。审计人员不因可以看日志就自动具备阅读全部文档正文的权限。

本模块覆盖登录租户切换、授权调整、问答访问、原文下载、同步身份使用和人工补偿等事件。记录内容以可追踪为目的，避免无必要地复制问题全文、答案全文和密钥。

## 审计事件

| 信息 | 用途 |
| --- | --- |
| 事件编号、发生时间、记录时间 | 排序、延迟判断与去重 |
| 主体、租户、发起者 | 区分用户、服务身份和代办 |
| 资源类型与标识 | 定位知识库、文档、任务或会话 |
| 动作与结果 | 区分尝试、拒绝、受理和完成 |
| 权限修订、请求编号 | 还原当时的判断依据 |
| 变更前后范围、理由 | 解释授权与撤权 |
| 关联任务及确认结果 | 追踪异步传播 |

拒绝事件也应可查，但错误详情不应向无权用户暴露受限文档名称或组织信息。日志中的标识与错误摘要按同一租户边界授权。

## 权限变更流程

1. 验证变更人的授权管理权限，校验新增或移除对象。
2. 计算影响范围，包括文档、用户组、缓存、服务身份和未完成任务。
3. 提交权限新修订与审计事件，记录变更生效时间。
4. 对收紧范围立即更新权威访问判断或阻断状态。
5. 派发索引权限、缓存、历史派生产物等刷新任务。
6. 查询关键访问路径验证新规则已生效。
7. 记录各副本确认与失败项；未完成传播不能被一个总状态掩盖。

权限已提交与全部副本同步完成是不同事实。界面应分别显示“访问规则已生效”“副本刷新中”，并说明当前采用的保护方式。

## 撤权与在途请求

| 阶段 | 处理基线 |
| --- | --- |
| 尚未检索 | 使用新权限，拒绝受影响文档 |
| 已召回、未生成 | 清理失效证据，必要时重新检索 |
| 已生成、未返回 | 再次校验，失败则不发送该结果 |
| 正在流式发送 | 检查到撤权后停止后续输出并标记中断 |
| 已返回或已下载 | 不能自动收回外部副本，记录访问事实 |
| 后台任务尚未发布 | 重新校验，阻止已失去授权的发布 |

对严格要求的内容，应评估禁用流式或增加完整输出检查。撤权边界和生效延迟需要由业务明确，而不是笼统承诺“实时绝对生效”。

## 审计查询与留存

按时间、主体、资源、动作、结果和请求编号查询。人工操作前后状态应可关联，批量操作保留批次与逐项结果。审计导出本身也需要授权和审计，避免通过日志侧绕过正文权限。

留存周期、访问限制、脱敏和删除政策由项目制定。需要保留证据时记录保留理由和到期时间；正文删除与审计摘要保留分别管理，不保证所有副本同时消失。

## 异常与恢复

审计写入失败时需定义动作政策。关键授权修改应与必要审计可靠关联，不能出现成功改权但无任何记录。普通访问日志可采用受控缓冲与补传，但丢失量必须可观测。

刷新任务失败时保留当前限制，不恢复旧权限“临时放行”。若误撤权，修复应创建新授权修订并再次审核影响，不能删除原审计记录制造未发生过的假象。

## 业务示例

员工从售后主管调岗为普通客服。成员服务提交新权限后，知识问答立即按新范围校验；相关答案缓存失效，内部赔付表引用拒绝访问。索引权限刷新失败产生待处理事项，但不会让旧权限继续支配答案。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 批量撤销一个用户组 | 可追踪影响范围和逐项传播结果 |
| 撤权后缓存仍未刷新 | 读取时被当前权限阻断 |
| 生成中发生权限变更 | 输出按定义的在途策略处理 |
| 人工恢复误撤权限 | 新事件关联旧事件，历史不可悄悄覆盖 |
| 审计导出包含其他租户 | 被范围校验阻止 |
| 副本刷新连续失败 | 告警且保护继续生效 |

## 实施决策

确定关键操作审计可靠性、留存周期、撤权时延目标、在途与历史答案策略、运维查看权限，以及权限传播失败的责任人与处理时限。
