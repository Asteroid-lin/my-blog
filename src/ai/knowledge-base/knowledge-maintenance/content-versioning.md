# 内容更新与版本切换

内容更新在保留文档身份的同时替换正文。业务目标是新内容完整生效、历史依据可追溯、失败可恢复，并防止旧任务覆盖新结果。所属场景：[知识更新与下线](./README.md)。

## 文档、版本与处理产物

| 对象 | 含义 |
| --- | --- |
| 文档身份 | 同一业务资料的稳定标识 |
| 内容版本 | 原始正文的一次确定快照 |
| 元数据修订 | 标题、标签、负责人等信息的变化 |
| 权限修订 | 可访问范围的变化 |
| 处理版本 | 解析、切分、嵌入配置不同产生的产物 |
| 有效版本指针 | 当前允许检索的内容与处理版本组合 |

同一份原文件重新用新解析器处理，不一定产生新的业务内容版本，但需要新的处理版本。业务上的生效日期和系统发布时刻分别记录，避免把“刚上传”理解为“现在适用”。

## 正常更新流程

1. 维护人员选择目标文档，提交新文件或正文及更新理由。
2. 验证操作权限、文档当前状态和调用方期望的旧修订。
3. 固定新内容快照，登记待处理版本和任务，保留当前有效版本。
4. 执行解析、切分、索引和质量检查。
5. 需要审核的知识库由审核人员比较差异并决定发布。
6. 发布时条件校验：旧指针仍匹配、目标版本仍获准发布、权限有效、文档未停用或删除。
7. 切换有效指针，记录发布者、发布时间与前后版本。
8. 让缓存和检索过滤使用新版本，旧产物进入保留与后续清理。

若检索设施不支持跨系统原子切换，应通过版本标识、查询侧核对及补偿保证业务可见性，不能直接假设“改数据库状态”就完成全部切换。

## 更新期间的可用性

默认基线是新版本构建期间保留已发布旧版本。若旧制度已明确失效，必须先停用旧内容，即使新内容还在处理，也不能继续提供失效答案。

首次上传没有旧版本时，处理失败意味着当前不可用。已经存在旧版本时，新版本失败只影响此次更新，不应把旧版本改成处理失败。

## 并发与乱序

| 情况 | 处理 |
| --- | --- |
| 两人基于同一旧版本提交 | 识别修订冲突，按产品规则选择审核或合并 |
| v3 先于 v2 完成 | 仅允许当前获准目标发布，v2 不得后来覆盖 |
| 更新期间调整标题 | 内容任务不能写回旧标题 |
| 更新期间撤权 | 发布按最新权限执行 |
| 更新期间删除文档 | 更新任务取消或过期，残留产物清理 |
| 旧版本回滚请求 | 重新检查权限、有效性与产物完整性后发布 |

来源版本不保证可排序时，以来源权威状态和本地操作修订判定过期，而不是比较版本名称。

## 差异、审核与历史引用

审核页面展示版本来源、正文差异、关键条款变化、质量报告和影响范围。涉及费用、期限、适用对象变化时，建议由业务负责人检查；具体审核规则由知识库决定。

历史答案保留当时的证据版本。新版本发布后，旧引用不能被悄悄改指到新内容。对用户可标注“该回答依据历史版本”，是否允许打开旧版本仍需按当前访问与留存政策判断。

## 回滚流程

回滚是一次新的发布操作：选择可用历史版本，验证来源仍允许使用、权限没有失效、索引产物可读取，再通过条件切换形成新发布记录。回滚不能恢复已撤销权限，也不能复活被禁止使用的旧政策。

如果历史索引已经清理，需要重新构建，不能把指针指向不存在的资源后标记成功。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 新版解析失败 | 原有效版本不受误伤，失败版本可追踪 |
| 新版部分索引成功 | 不作为完整版本发布 |
| v2 晚于 v3 返回 | 不回退到 v2 |
| 正文与标题同时更新 | 两个维度不会相互覆盖 |
| 更新中删除文档 | 后续任务不能重新激活 |
| 回滚历史版本 | 有新的发布审计，仍满足当前权限 |

## 实施决策

确定并发更新策略、审核范围、业务生效期规则、版本保留数量、回滚权限，以及失效制度是否允许在更新期间继续使用。
