# 失败重试与任务恢复

恢复机制让临时失败、进程退出和外部结果未知得到可追踪处理。目标是最终完成正确业务意图，同时防止重复执行、旧版本覆盖和长期卡住。所属场景：[知识更新与下线](./README.md)。

## 失败分类

| 类别 | 例子 | 处理原则 |
| --- | --- | --- |
| 临时失败 | 超时、限流、短暂网络错误 | 有预算地退避重试 |
| 输入不可处理 | 文件损坏、缺少必要字段 | 修正输入后新建或重试明确阶段 |
| 授权或配置错误 | 密钥失效、目标无权限 | 暂停相关任务，修复授权 |
| 业务冲突 | 旧版本、文档已删除 | 取消或标记过期，不强行执行 |
| 结果未知 | 外部已执行但响应丢失 | 先查询与对账 |
| 永久不支持 | 组件不支持此格式 | 返回明确原因，走替代流程 |

重试次数耗尽意味着需要升级处置，不意味着业务一定没有执行。结果未知必须保留核对入口。

## 任务状态与检查点

建议区分待执行、执行中、等待重试、待人工、成功、失败和取消；任务阶段另外记录下载、解析、切分、索引、发布、回写或清理。

每次尝试记录执行者、领取代次、租约期限、输入版本、阶段产物、错误类别、下次执行时间和外部请求标识。成功产物只有在输入和配置版本匹配时才可复用。

## 自动恢复流程

1. 查询到期待执行、等待重试或租约过期任务。
2. 通过条件更新领取任务并产生新的领取代次，避免多个执行器同时取得提交权。
3. 重新检查文档状态、目标修订、租户与来源权限。
4. 读取检查点，确认上一步是否真正完成；结果未知时查询外部状态。
5. 从安全阶段继续，重复外部调用沿用同一业务幂等标识。
6. 长任务持续续租；失去租约后停止后续可控副作用。
7. 完成写入时校验领取代次与状态，拒绝旧执行器提交。
8. 超过预算或无法自动判断时转人工，并附证据。

只续租而不检查业务进度可能让死任务永远占用。应区分存活心跳与阶段进展，并对长期无进展设置独立处置。

## 重启、租约与定时漏跑

硬退出通常无法立即释放租约，恢复执行需要等待到期或经过受控接管；因此恢复时间由租约、扫描周期和排队共同决定。

调度触发记录不能替代业务完成记录。例如先记下本次定时槽位已领取，随后进程在创建任务前退出，重启又因为“该槽位处理过”而跳过，就会漏跑。应采用持久触发记录与可恢复批次，或明确补扫策略，核对“槽位已领取”和“批次已建立”的差异。

同一套恢复机制不能只处理文档任务，还应覆盖扫描批次、结果回写和物理清理各自的未完成事项。

## 重试策略与幂等

指数退避配合随机扰动可减少大量任务同时重试；并发、最大次数、总时长和费用预算应按服务与错误分类配置。输入错误不适合高频重试，权限错误不适合持续消耗外部接口。

同一业务请求重试应表达相同意图；同一幂等标识对应不同参数应返回冲突。相关设计思路参考 [AWS 关于幂等 API 与安全重试的说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)，本专栏的任务状态与恢复规则需在具体服务中实现。

外部系统不支持幂等或结果查询时，无法仅靠本地记录保证不重复执行。应引入明确的人工核对或可补偿流程，并记录这一边界。

## 人工恢复操作

| 操作 | 适用情况 |
| --- | --- |
| 重新查询结果 | 外部执行结果未知 |
| 重试失败阶段 | 输入有效、临时错误已解除 |
| 修正配置后重试 | 授权、路由或额度已恢复 |
| 新建替代任务 | 输入内容或业务意图已变化 |
| 取消过期任务 | 新版本已取代，或文档已下线 |
| 清理残留资源 | 任务不再需要，但有已生成产物 |

禁止通过直接改“成功”状态来掩盖缺失产物。人工确认需要检查目标文档、索引、有效版本和实际业务结果，并保留操作理由与证据。

## 验收场景

| 故障注入 | 预期 |
| --- | --- |
| 下载后进程退出 | 从匹配版本的检查点恢复 |
| 外部创建成功但响应超时 | 先核对，不无条件重复创建 |
| 租约过期后旧执行器返回 | 不能提交新状态或覆盖有效版本 |
| 定时槽位记录后、建任务前退出 | 能恢复该批次或按政策补扫 |
| 文档下线后恢复旧任务 | 不重新发布，残留可清理 |
| 大量限流错误 | 重试有节制，正常任务不被全部堵塞 |

## 实施决策

确定错误分类、租约与续租、重试预算、扫描补跑策略、人工权限、外部幂等能力和恢复时限，并用实际故障演练验证。
