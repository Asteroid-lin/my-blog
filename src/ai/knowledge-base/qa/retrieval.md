# 多路召回与过滤

召回从允许访问的知识中找出可能支持回答的候选片段。这个阶段关注覆盖率与访问边界，不能把“有候选”直接解释成“已有正确答案”。所属场景：[知识检索问答](./README.md)。

## 输入、输出与业务目标

输入是检索问题、明确的知识范围、业务过滤条件和策略版本；输出是候选片段、文档与版本、来源位置、各召回通道及分数。对用户而言，需要既能找到术语相近的解释，也能准确定位产品编号、错误码和制度名称。

## 召回通道

| 通道 | 适用问题 | 主要限制 |
| --- | --- | --- |
| 关键词检索 | 产品编号、错误码、专有名词、精确表达 | 同义改写可能漏召回 |
| 向量检索 | 口语提问、语义相近、表达不同的内容 | 相似不代表事实适用 |
| 结构化筛选 | 地区、产品、日期、文档类别 | 元数据错误会造成误过滤 |
| 指定文档内检索 | 用户已明确某份文档 | 范围过窄时可能没有完整证据 |

可以组合通道，但不应假定越多越好。新增通道需要通过评估证明收益，并衡量延迟、成本和误召回。

## 正常流程

1. 从服务端授权上下文生成不可被用户覆盖的租户和访问过滤条件。
2. 确认知识库启用、文档未停用，并选择当前有效版本。
3. 根据问题类型执行关键词、向量等检索。向量查询使用与索引兼容的模型配置。
4. 收集各通道候选，对不同分数体系进行明确的合并或排序处理。
5. 按文档版本和片段身份去重，保留命中通道及来源信息。
6. 再次核对候选的当前访问权限、有效版本和内容可读性。
7. 对候选覆盖情况作初步判断，再交给重排序与上下文组织。

过滤应尽量在检索服务产生候选时生效。服务端结果复核属于额外保障，不能先把未授权正文发给模型，再依靠回答阶段隐藏。

## 范围与有效版本

召回范围同时受租户、知识库、文档权限、有效内容版本和业务条件约束。授权服务不可用、身份上下文缺失时停止受影响查询。只允许在权限能可靠确认的范围内继续，不取消过滤扩大搜索。

当检索引擎无法直接按每份文档的当前版本过滤时，应结合发布策略和权威版本复核，避免旧版本占满候选。必要时扩大授权范围内的初始候选量再校验，但必须受资源预算限制。

## 分数、阈值与候选量

不同模型和通道的分数不能直接相加当作统一可信度。合并方法、候选量、阈值与通道权重应形成策略版本，通过样本调优。高分只表示算法判断更相关，不代表来源权威、内容最新或结论正确。

检索页面和日志中记录原始通道、排序位置和排除原因，方便区分“没搜到”“搜到了但被过滤”“进入候选后被排序淘汰”。

## 无召回与降级

| 情况 | 处理 |
| --- | --- |
| 当前范围没有候选 | 返回无匹配证据，可提示补充产品或调整已授权范围 |
| 向量服务失败、关键词可用 | 仅在已批准策略下单通道降级，记录状态 |
| 权限过滤服务失败 | 停止相关检索，不取消权限条件 |
| 候选全部来自失效版本 | 按索引一致性故障处理，不能回答旧政策 |
| 少数知识库超时 | 按产品策略返回部分范围结果并明确覆盖限制，或整体失败 |

系统故障与知识缺失是不同结果。不能把检索服务超时包装为“知识库中没有答案”。

## 业务示例

问题为“X200 报 E17 怎么处理”。关键词通道命中 X200 的 E17 条款，向量通道还命中 X100 类似故障。候选阶段可以保留相关内容，但产品筛选与后续排序应识别型号差异，不能仅凭语义相似把 X100 的操作作为 X200 的答案。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 明确编号或错误码 | 精确资料能进入候选 |
| 使用业务同义词 | 有对应知识时能形成可评估召回 |
| 其他租户拥有高度相似内容 | 候选和模型上下文均不含该内容 |
| 文档刚被停用 | 即使索引尚未清理也不能进入回答 |
| 多通道命中同一片段 | 去重但保留通道证据 |
| 检索接口超时 | 报告失败或受控降级，不能误报无答案 |

## 实施决策

确定通道组合、候选预算、降级政策、版本过滤能力及无匹配时的产品交互。评估口径见[检索效果评估](../quality-operations/retrieval-evaluation.md)。
