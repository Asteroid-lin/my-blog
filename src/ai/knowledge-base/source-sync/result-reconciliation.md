# 同步结果与状态对账

本模块确保来源、同步平台和目标知识库对“哪份文档、哪个版本、处理到哪一步”有可核对记录。回写失败与目标处理失败分开管理，避免为了补一条结果而反复重建知识。所属场景：[外部知识源同步](./README.md)。

## 三类状态

| 状态维度 | 示例 | 回答的问题 |
| --- | --- | --- |
| 执行状态 | 待执行、执行中、成功、失败、取消 | 任务自身是否结束 |
| 目标业务状态 | 待发布、可用、停用、删除中 | 文档能否参与问答 |
| 结果回写状态 | 无需回写、待回写、回写成功、重试中、待人工 | 来源是否确认收到结果 |

例如任务执行成功、目标可用、回写重试中，是合法组合。不能将回写异常反向改成“目标未创建”，也不能在回写成功后认为所有后续目标状态永远有效。

## 结果记录与回写内容

记录租户、来源配置、源文档身份、操作修订、任务编号、目标文档、有效版本、执行结果、完成时间和错误分类。协议需要的话再记录错误摘要与原任务关联。

回写不应包含密钥、签名下载地址、未经授权的正文或内部堆栈。来源只需要知道业务结果和可追踪编号，完整诊断信息放在受控日志。

## 正常流程

1. 目标处理完成后，可靠保存业务结果并登记待回写事项。
2. 回写执行器领取事项，按照来源协议发送带幂等标识的结果。
3. 检查来源返回的业务确认，不把“网络请求已发出”当作确认。
4. 成功后记录确认时间；失败保留尝试次数、下次时间和错误原因。
5. 重复发送同一结果时保持业务语义一致；源版本已变化时避免把旧结果覆盖成当前状态。
6. 对账作业定期检查未确认结果、无目标映射、状态不匹配和孤立资源。
7. 将可自动修复的问题交给补偿任务，涉及业务判断的差异转给负责人。

结果可存独立事件表，也可作为任务中的持久字段；关键是目标结果和待回写意图可靠关联，并支持独立扫描恢复。

## 对账维度与处理

| 差异 | 可能原因 | 建议动作 |
| --- | --- | --- |
| 来源有文档、平台无任务 | 扫描漏项或游标问题 | 补扫描并登记任务 |
| 平台成功、目标查不到 | 映射错误、外部删除或索引丢失 | 核实后重建或修正记录 |
| 目标新版本、平台旧版本 | 提交结果丢失 | 按来源与任务证据补记 |
| 目标仍可用、来源已撤权 | 权限同步延迟 | 优先阻断访问再修复同步 |
| 目标已成功、来源显示处理中 | 回写失败或响应丢失 | 查询回写结果或幂等补发 |
| 目标存在但无来源映射 | 中途失败留下资源 | 追踪任务，认领映射或清理 |

数量相同不代表内容一致。至少抽核来源身份、内容版本、权限修订和可检索状态；相同名称不能证明是同一文档。

## 异常、超时与幂等

回写超时意味着结果未知，不等于来源没有处理。优先查询确认；没有查询能力时用固定事件标识重发，由接收方去重。若来源不支持幂等，应设计可重复覆盖同一修订状态的协议，或转人工核对。

旧版本的失败通知晚于新版本成功到达时，接收方需要按操作修订识别历史结果，不能把当前成功状态回退为旧失败。无法改造来源时，回写端至少限制过期事件影响当前状态，并保留历史审计。

## 运营页面与责任分工

运营列表建议分成执行异常、回写异常、状态差异三类视图，共享来源文档和任务编号。知识维护人员确认内容，集成负责人处理协议或授权问题，运维处理连接与积压。每条人工操作记录操作者、原因、前后状态和关联任务。

人工操作应提供“重新回写”“重新核对”“补同步”等明确意图，避免一个万能“重试”从头重复所有步骤。

## 业务示例

文档 v3 已发布，回写请求超时。用户可以正常检索 v3，运营看到“可用，结果待确认”。执行器查询来源已收到同一事件后补记成功；如果未收到，只重发 v3 的结果。随后 v4 完成时，晚到的 v3 结果只能作为历史记录。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 回写连续失败 | 目标保持原业务状态，回写可独立恢复 |
| 来源重复收到成功结果 | 不产生新的同步或重复业务单据 |
| 成功响应丢失 | 查询或补发后最终状态一致 |
| 新成功后收到旧失败 | 当前版本不回退 |
| 相同数量但文档映射错位 | 对账能发现差异 |
| 人工补偿 | 有明确操作类型与审计记录 |

## 实施决策

确定来源是否需要回写、确认协议、幂等保留时间、对账频率、差异处理时限及哪些差异允许自动修复。
