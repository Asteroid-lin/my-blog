# 评估样本与基准集

评估集把“好像回答得不错”转成可重复检查的业务事实。每条样本都应说明谁在什么知识范围内问什么、有哪些可用证据、预期怎样回答或拒答。所属场景：[质量评估与运营](./README.md)。

## 样本来源与责任

业务人员提供高频问题和正确处理依据，知识维护人员核对文档版本，测试人员设计边界和异常，系统运营从失败问答与反馈中补充样本。最终标准由熟悉业务规则的人确认，不能仅以模型自己生成的答案作为真值。

真实用户记录经过授权、脱敏和用途确认后才能进入评估集。公开博客中的示例使用虚构业务数据，避免把内部资料复制到公开文档。

## 样本字段

| 信息 | 内容 |
| --- | --- |
| 样本编号与类别 | 唯一身份、业务场景、难度和风险类别 |
| 原始问题与上下文 | 单轮问题或必要多轮历史 |
| 用户、角色、租户范围 | 使用可复现的测试身份与授权 |
| 知识快照 | 文档版本、有效状态和权限修订 |
| 参考证据 | 支持结论的文档、片段或来源区间 |
| 预期结论与要点 | 允许不同表达，但关键条件必须满足 |
| 预期行为 | 回答、澄清、部分回答、拒答或报故障 |
| 标注人与复核人 | 支持争议处理 |
| 样本修订与有效期 | 防止过期答案持续充当标准 |

知识内容更新后，保留旧基准用于历史回放，并为新知识建立对应修订，不把两套答案混用。

## 覆盖矩阵

| 类别 | 例子 | 检查目标 |
| --- | --- | --- |
| 高频明确问题 | “寄修运费由谁承担” | 基本可用性 |
| 业务条件分支 | 在保、过保、人为损坏 | 条件完整性 |
| 精确标识 | 型号、错误码、制度编号 | 关键词能力 |
| 口语与同义表达 | “机器坏了寄过去谁付快递” | 语义召回 |
| 多跳与跨文档 | 维修费用和物流规则 | 证据覆盖 |
| 多轮追问 | “超过保修期呢” | 上下文理解 |
| 无答案与冲突 | 知识没有规定、两份制度矛盾 | 适当拒答或澄清 |
| 权限与生命周期 | 撤权、停用、旧版本 | 隔离与时效 |
| 故障与恶意内容 | 超时、资料中的越权指令 | 异常边界 |

比例根据真实业务流量与风险决定，同时保留低频但严重的失败样本，不能只选择容易得到高分的问题。

## 建集流程

1. 明确评估目标，例如切分调整、模型替换或上线验收。
2. 从真实业务抽样并补充边界案例，记录选样依据。
3. 固定知识快照和测试身份，防止运行过程中来源漂移。
4. 标注参考证据、必须包含的条件和不允许出现的结论。
5. 由另一位具备业务判断能力的人复核争议样本。
6. 划分调优集与独立验收集，限制验收集被反复用于调参。
7. 发布基准版本，保存配置、执行规则与样本清单。
8. 定期维护失效样本，并将线上真实失败补充为回归用例。

不要把参考答案本身额外写入待检索知识，只为让系统在评估中命中；也不要将测试问题和答案直接作为提示词中的示范而又宣称是独立验收。

## 参考答案的形式

制度问答可以采用“结论 + 条件 + 证据”的要点式标准。例如必须包含“在保且非人为损坏免维修费”“运费由客户承担”，但不要求逐字相同。

对于无法回答的问题，标准应描述需要澄清什么或为什么证据不足。系统故障样本的标准是正确报告故障，不是生成一个参考业务答案。

## 样本变更与异常

发现标注错误时创建修订并重跑受影响评估，不直接覆盖历史结果。权限测试身份失效、知识快照缺失和外部接口不可用应标记运行无效或失败，不能从分母中悄悄移除以提高成绩。

标注人之间存在分歧时，记录分歧原因并由业务负责人裁定；如果业务本身尚无统一规则，该样本应期望系统说明不确定性。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 同一基准重复执行 | 输入、知识范围与版本可以还原 |
| 文档政策变化 | 新旧基准独立，不误用旧答案 |
| 无答案样本 | 有明确的拒答或澄清标准 |
| 权限样本 | 能验证候选、回答及引用访问 |
| 测试环境异常 | 结果被如实记录，不静默丢弃 |
| 同题不同表达 | 按业务要点判断，而非文本完全相等 |

## 实施决策

确定各业务样本覆盖量、标注责任、验收集管理、敏感数据处理及样本更新周期。所有样例分数与演示结果必须标明其是否来自真实运行。
